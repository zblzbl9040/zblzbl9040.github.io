mTLS双向认证：从选型到落地的完整实践

问题背景

在分布式集群中，关键组件之间的通信往往没有安全认证机制——只要知道 IP 和端口，任何节点都能直接加入集群、参与通信。这在内网环境下看似问题不大，但一旦网络边界被突破，整个集群就完全暴露。

本文记录一次给集群组件间通信加认证机制的调研与落地过程，最终方案是 mTLS + CA 双向认证。

可选方案对比

1. 静态共享 Token

在配置里写一串密钥，所有节点一样，请求带上它，服务端做字符串比对。

  • 优点：实现极其简单
  • 缺点：全局公用一个 token，一处泄露全局崩溃；token 可被抓包；数据传输不加密

2. HMAC 签名请求

密钥依旧是共享的，但不直接发送。每个请求用密钥计算 HMAC 签名，只发签名和时间戳，服务端用同样的密钥重算并比对。

  • 优点：密钥不上网络；时间戳可防重放
  • 缺点：密钥仍是全局共享；数据传输不加密

3. 身份密钥环验证

每个实体初始时拥有自己的密钥，密钥从不上线，由一个可信的”密钥管家”服务发放短期会话密钥，每次建立连接时做认证握手。

  • 优点：每个实体拥有独立密钥，不全局共享；密钥不上线；可防重放
  • 缺点：数据传输不加密；需要额外的密钥管家服务；初始密钥的分发和同步有效性认证困难

4. mTLS + CA 双向认证 ✅

双方都持有证书，建立连接时互相认证。证书由 CA 统一签发和吊销。

  • 优点：双向认证；数据传输加密；密钥、证书可自动颁发；技术标准成熟
  • 缺点：部署较为复杂；监听端口固定时，所有访问该端口的服务（如 CLI 客户端、网关等）都需要做 mTLS 认证

方案选择与一个坑

最终选择 mTLS：既能完成双向身份认证，又能保证传输加密。

但单纯配置 mTLS 有一个容易被忽略的问题：它只能保证集群初始建立时的安全，==不能完全保证==新节点加入的安全。以 3 节点 Raft 集群为例：把新节点 m4 加入成员表只需要 m1/m2/m3 三个老成员投票，m4 自己并不参与。这样一个没有证书（或没开 TLS）的 m4 依然可能被加进成员表——只是加入后它无法和其他节点通信，集群处于一种”半残”状态。

解决办法：在把新节点加入成员表之前，先做一次 TLS 连通性检查（拨号新节点），TLS 握手通过才允许加入。

  4. ==服务端进行对应的解密和验证==

落地时要考虑的问题

把 mTLS 作为集群组件间的认证方式，需要考虑：

  1. 在最开始的 Leader 选举阶段，每个节点会在 Client 和 Server 角色之间来回切换，证书必须同时支持两个方向；
  2. 证书怎么签、什么时候签、谁来签；
  3. 身份体系如何设计；
  4. 如何批量签发所有的子证书。

利用 OU 字段做角色授权，可以在 TLS 握手完成后从对端证书中读出角色，实现”连接级”的权限控制。当前阶段只做连接控制，暂不做端点级控制（连接进来就信任此角色，不卡具体端点）。

长连接复用

为了避免每次 RPC 都重新建立连接（尤其是 TLS 握手开销不小），可以做一个类似连接池的机制：

创建 TCP/TLS 连接后放入连接池并维护引用计数，以目标地址 host:port 作为索引键。发请求时先拿目标地址去池里查，查到就把这条已经握过手、正开着的连接”借”出来用；没查到才执行拨号，建成后存入池中。

连接会在以下情况下断开并从池中移除：RPC 出错、池满了被淘汰、对端关闭、网络断开、进程退出。

总结

mTLS + CA 的组合为集群内部通信提供了双向身份认证和传输加密，配合基于证书 OU 的角色授权和新节点入队前的 TLS 预检查，能覆盖从集群建立到动态扩容的全生命周期安全。核心要点回顾：

  1. 单纯 mTLS 不保护”新节点加入”流程，需要额外的入队前 TLS 预检查；
  2. 证书字段各司其职：CN 审计、OU 授权、SAN 做 TLS 校验、Issuer 做根认证；
  3. 选举类场景下节点角色会切换，叶子证书的 EKU 要同时含 serverAuth 和 clientAuth；
  4. 用配置清单 + 脚本实现批量签发，用 Enabled 开关支持灰度切换。

一、《大规模万亿大模型训练与推理存储挑战及优化》

AI大模型正向”万亿参数”和”百万Token上下文”的规模发展，存储已进入前后台计算的关键路径。

在AI Coding场景下，AI Coding需要多轮上下文本交互，极其依赖KVCache；AI Agent需要数十轮长程推演和超并发，==存储状态的共享、迁移与恢复决定了端到端效率==。

为此，阿里云提出了一套从一体机到集群、从千卡到万卡的全覆盖AI存储解决方案：

底层为APFS并行文件系统，中间新增了一层新的Fusion Cache（近计算缓存）用来服务上层的模型训练和推理。

近计算缓存的核心思路是把数据”拦截”在算力设备附近的存储介质上，来解决大模型推理时访问远端存储高延迟、大带宽占用的问题。（个人理解是直接将数据卸载到本地存储介质上，来避免网络传输延迟）

基于这样的架构，模型训练的核心挑战从”带宽不足”变为”千节点并发下的低一致性瓶颈与故障放大”。

这里的”千节点并发下的低一致性瓶颈与故障放大”主要体现在两个方面：

  1. 低一致性瓶颈：传统文件系统为了确保数据一致性，通常采用”强一致性”锁机制。但是在大模型训练时，成千上万个节点会同时去读写海量的小文件（数据集切片）、频繁创建/删除临时文件、以及在CheckPoint时同时写模型权重。这导致了==元数据锁争抢== + ==单点瓶颈==：
    • 元数据锁争抢（主要原因）：比如有1000个节点同时请求”在同一个父目录下创建文件”，为了保持一致性，文件系统必须先加锁（父目录锁），然后分配inode，再分配数据块，最后解锁；
    • 单点瓶颈（次要原因）：所有节点都要去请求中心化的元数据服务器，或者争夺同一个锁。这不仅导致每秒的元数据操作数（IOPS）极低，还导致延迟迅速上升。
  2. 故障放大：大模型训练是一个高度同步的过程。几乎所有的GPU都在一个计算迭代（Step）里，必须等所有人把数据都准备好、把梯度同步完，才能进行下一步。这会出现三个问题：==非抢占式锁与慢节点== + ==同步屏障== + ==异构硬件故障率高==：
    • 非抢占式锁与慢节点：如果某个节点因为硬件老化（比如PCIe降速）、网络丢包变成了所谓的”慢节点”，它会占用着锁不放，其他节点为了等这个锁，只能被迫排队；
    • 同步屏障：在同步训练模式下，只要有一个节点慢，整个集群都要等它；如果它一直不恢复，整个训练任务就会超时中断。一旦任务重启，几千张卡上的CheckPoint都需要从存储里重新加载；
    • 异构硬件故障率高：千卡集群中，网卡、光模块、交换机的故障率是极高的，在这种高度耦合的存储架构下，故障会影响全集群。

为了解决上面提到的问题，提出了如下解决方案：

  1. 针对锁的问题：提出资源预分配、异步申请、批量授权，提前把资源分给各节点，尽可能避免锁竞争。此外，使用全分布式打散与集中管理相结合的方式进行管理。（个人理解是：同一把大锁拆分成无数个分片锁，分布在不同机器上并行处理；同时保留一个集中管理模块来宏观调控）

  2. 针对慢节点问题：提出持续沉淀飞行检查案例库与周期性巡检 + Bonding技术：

    • 持续沉淀飞行检查案例库与周期性巡检：引入类似”哨兵”的机制，会总结历史上出现的各种节点故障、PCIe降速等案例，定期主动激活去检查所有的计算节点，一旦发现某节点延迟过高或报错，系统会果断将其剔除（针对节点问题的处理）；
    • Bonding技术（网卡绑定）：多条链路备用，一条链路断了，其他链路毫秒级自动顶替。”多路径重选和协议降级”保证即使路不通了也能绕道走或者降低标准先传过去（针对网络问题的处理）。

  3. 针对存储节点：提出分组与多副本 + 故障域设计。确保数据在物理上有多份副本保障；结合故障域设计，把副本放在不同的机柜或机房，避免大片的单点故障；数据与元数据分离是为了避免管理海量数据的节点被数据读写拖垮。

此外，为了优化集群级有效算力和控制TCO，提出了如下解决方案：

  • 左侧（传统模式）：存储任务（FS、块IO）跑在主机的Host OS内核里，必须占用CPU资源，再通过NIC去访问APFS；
  • 右侧（DPU卸载模式）：将FS、块IO、协议栈全部下放到专用的DPU芯片上，主机CPU只负责”用户线程”和”计算任务”。

用到的核心技术：Virtio-FS性能优化（虚拟化传输）、DMA/零拷贝（数据不经过CPU内存直接传）、EC/CRC硬件卸载（交给DPU芯片算），以及组件资源开销优化：

  • Virtio-FS：利用宿主机与虚拟机”共置”的特性，通过共享内存和DAX技术绕过宿主操作系统，极大减少了通信层数，让高速端到端网络路径尽可能直连，不需要频繁调用系统内核切换内核态与用户态；
  • DMA/零拷贝：利用专用硬件（如RDMA）将数据直接从内存放入存储，全程不经过CPU；
  • EC/CRC硬件卸载：让网络适配器（NIC）在数据流经时边传边算，直接将硬件算力用于存放校验码，避免线程调度；
  • 组件资源开销优化：让DPU优先处理长连接关键流量，把短暂的突发流量留给CPU处理。

下图讨论了在模型训练时，KVCache的决策，即KVCache的卸载过程需要考虑以下内容：

  • 缓存命中的总开销必须小于重新PreFill（预填充）的开销：

    重新计算的路径是：排队 -> 重新PreFill -> Decode；缓存命中的路径是排队 -> 查找 -> 读取 -> 网络 -> 注返 -> Decode。虽然缓存命中省去了耗时的PreFill，但引入了查找、读取和网络传输的额外开销。右侧的曲线给出了策略：==复用概率高时，优先缓存；复用概率低时，直接重算==。如果网络太慢，读取缓存比现算还慢，那就不缓存。

  • 在实际卸载时，系统必须同时回答四个问题，全部通过才允许卸载：

    1. 值不值得缓存：重算的成本，能否覆盖读取、传输和注返（注入到显存）的开销？
    2. 能不能准确命中：租户、模型、版本、前缀与KV格式必须完全一致，如果换个模型乱命中，产生的就是”脏数据”；
    3. 能不能及时取回：带宽是否足够？排队是否会阻塞？必须满足用户的SLO；
    4. 异常时怎么办：网络抖动导致Miss、超时或数据异常了怎么办？系统必须能快速回退重算，不能让请求挂死。

Fusion Cache的产品结构：

  • 最上层（PPU节点）：推理引擎运行在带HBM和CPU Memory的PPU（加速计算芯片）节点上，HBM最快但最贵，只能放最活跃的数据；
  • 中间层（推理加速组件）：包含多级缓存、智能路由、预取加速、全局共享、高速通信，这些组件负责智能判断数据怎么写、怎么读；
  • 下一层（本地NVMe + Fusion Cache Pro）：通过RDMA高速网络，将多台机器的本地NVMe打通，形成一个”近计算多机分布式存储池”，实现跨实例共享；
  • 最底层（Fusion Cache APFS）：提供底层的”服务池级共享持久化存储池”，实现本地/远端分层，以及计算与容量的彻底解耦。

二、《规模化AI存储架构设计——分层与解耦架构为何至关重要》

1. AI数据全景概览

IDC预测：2028年全球数据生成量将达到394ZB，2023-2028年复合年增长率高达24%。且图像、音频与视频密集型AI模型是当前存储需求的最核心驱动力。

2. 超大规模客户分层存储的成熟实践

经过统计，约80%的云存储是基于HDD的。因此提出了”数据周期需要分层存储架构，每个阶段匹配适合的存储介质以优化TCO“的核心理念。

  • 数据摄入/准备阶段：使用冷存储/温存储（HDD为主，容量优先，带宽为辅）；
  • 训练阶段：使用温存储（HDD为主，性能优先，容量为辅）；
  • 推理阶段：因为需要极速读取，使用温/热存储（HDD & 闪存，带宽与容量并重）。

为了降低TCO，给出了不同存储介质的成本对比：

对于1EB容量、5年期的总拥有成本：QLC全闪存高达7.29亿美元，而CMR HDD只需1.43亿美元，SMR HDD最便宜，只需1.221亿美元。SMR比全闪存便宜约6倍，比CMR便宜约15%。且在五年周期内，SMR对CMR的累计成本优势从1460万美元扩大到了2110万美元。

同样是承载1EB数据，SMR只需要55个机架，CMR需要72个，QLC需要61个。SMR相比CMR节省了17个机架（约-24%），这不仅意味着更少的磁盘柜和交换机，更意味着大幅降低数据中心极其昂贵的电力消耗。

3. 西部数据开放软件生态

西部数据将其高密度硬盘与Ceph、IBM Storage Scale、BeeGFS、Leil等主流存储软件进行了联合测试与适配，证明了分层存储理念能够在TCO优化上有重要的作用。

三、《智能体时代存储的新机遇和挑战》

过去的对话式推理是短上下文、临时缓存、低并发；现在进入Agentic智能体时代，变成了多轮工作流、超长上下文、可复用长期记忆、自我派生增长。这直接激化了==“HBM的高昂成本”与“推理负载需要高效复用”==之间的矛盾。

由于长上下文的发展趋势，存储厂商必须通过多级存储来平衡成本。这就引入了一个新的问题：选择本地存储还是外部存储。

由于外部存储是一个可共享分离的NVMe Pool，核心优势是池化、共享，能带来更大的容量、性能和更优的数据管理，相比于本地存储更具优势，因此使用外部存储作为KVCache的底层大容量共享底座，为智能体提供长期的持久化存储。

GPU真正在算的时间才是产出的时间。当KVCache加载时间小于计算时间时是”纯收益”，大于时就是”负收益”（在第一个议题中也有表达）。这个平衡点称为”黄金交叉点”。理想的卸载率要无限接近100%，但又要保证不产生延迟。

此外，AI工作流中的大模型（特别是稀疏注意力模型）产生的新数据特征，与底层传统存储架构能提供的IO特性之间存在严重的”错配”问题：

  • 左侧部分：大IO顺序读取。存储把整块巨大的KVCache数据，全部通过大IO顺序加载到HBM里，然后再由GPU上的”Top-K selector（选择器）”挑出其中真正需要的token送给Sparse Attention（稀疏注意力）。这样的负载对存储系统极其友好，但是对HBM的计算资源造成了浪费，因为存在着大量无效读取；
  • 右侧部分：小IO稀疏读取。存储精确识别出真正需要的token，直接把它抽取出来（Sparse Retrieved），跳过HBM的大块预加载，直接放进HBM，然后再喂给稀疏注意力。这样的操作极大地节省了HBM空间和传输的数据量，但是这样的随机小IO对存储系统来说是一个巨大的挑战（寻址开销大，存储的带宽发挥不出来，排队延迟增加）。

在这种稀疏化小IO场景下，传统以CPU为中心的架构中，CPU已经成为系统的主要瓶颈：

  • 从GPU服务器侧看，一颗CPU无力承担多至8路GPU的巨大IO并发；
  • 从外部存储节点看，4张网卡和24/36块NVMe的并发能力也已经远超CPU处理能力。

为了解决上述瓶颈，提出了”CXL内存 + NVMe全闪”和”DPU直通”的双架构，并推出了软硬件一体的Xcache方案。它可以向上兼容NVIDIA、昆仑芯、沐曦等所有异构算力，以及vLLM、SGLang、TensorRT-LLM等推理引擎。

1. 硬件架构

CXL高性能可共享内存池：

利用CXL 2.0协议，把多台服务器的内存池化，做成”千TB级”的CXL内存框。它用Load/Store直接内存级访问语义，实现KV的精准稀疏读取和”智能挑选”，时延低至亚微秒。

为了解决大小IO错配问题。

把DPU放进存储盘柜里，通过NVMeoF KV标准协议互通。DPU硬件加速IO栈，绕过CPU的协议解析，实现原生KV直通，让KVCache拥有长期记忆和灵活共享复用，兼容传统CPU主控模式。

解决CPU瓶颈问题。

2. 软件架构

有了上面的这些硬件，Xcache分层存储结构从快到慢划分出了6层：

  • G1（HBM）和G2（Local Memory）：放当前最热的、机架内复用的数据；
  • G2.5（CXL Memory）：CXL内存框，放跨节点的稀疏复用、POD共享和长期记忆；
  • G3（Local/Rack SSD）：放前缀复用；
  • G3.5（CMS / EBOF盘框）：EBOF，放PB级容量、可靠存储的KV，延迟是亚毫秒级；
  • G4（分布式存储）：通过POSIX RDMA（毫秒级），放上百PB级的集群共享、历史长期记忆。

此外，通过KVCache原生的分布式存储系统软件来实现对硬件的调度：

  • CMS Backend：由于在硬件上通过NVMeoF KV标准协议实现了互通，因此CMS存储可以直接KV -> DPU -> NVMe盘，不再需要中间的文件系统层。因此数据不需要被拆成块，直接以键值对的形式在底层被命中并读取，且KV的读写指令都由DPU硬件卸载完成，绕过了主机CPU的干预；
  • 命名空间：对于离散型KV（如多轮对话中互不相干的独立上下文），CMS采用DHT一致性HASH算法来打散，保证了数据均匀分布在所有存储节点上；对于Radix索引型KV（长上下文常见的结构），它们有大量的公共前缀，CMS采用按子模分裂打散，把公共前缀提取出来共用，底层用Radix树结构来组织；
  • 空间索引：针对离散型KV，使用动态hash索引；针对Radix型KV，使用ART树索引。

四、《面向低带宽传输和存储的视觉语义编码技术与标准——机器视觉编码技术与标准进展》

背景

在过去30多年来，视频标准从MPEG-2、H.264、H.265到H.266，每一代追求的都是压缩效率翻倍，这些的主要驱动力是5000亿视频服务+5700亿智能手机这个市场。

80%的人类感知来自视觉，视频流量占网络主流。更重要的是，机器视觉是AI最大的应用领域，大多数5G应用场景都跟机器视觉有关，市场规模正在暴涨，传统的视频编码已经跟不上了。

传统的视频编码协议都是为了给人看，最终的目标是感知质量。但是在机器视觉中，模型看视频主要是为了提取特征。

这里主要想体现的是：在机器视觉的应用中，传输数据时，没必要把客观世界的完整视频传过去，只需要把机器需要的特征传过去就行了。

通过限定的码率下，最小化机器视觉任务的损失，实现压缩率与任务准确率的平衡。这能在极低带宽下，实现极高的压缩比。

为了解决上述的问题，提出了”面向机器视觉和人机混合视觉的压缩编码”：

左侧部分（编码端）：

  • Temporal resample（时域重采样）：降低帧率。机器识别动作不需要像人类眼睛一样看30帧/秒，可能5帧/秒就足够了，这直接减少了大量时间维度的冗余；
  • Spatial resample（空域重采样）：降低分辨率。机器进行目标检测时，把4K降采样到1080p甚至720p，不影响机器的识别；
  • Task-based preprocessing（基于任务的预处理）：基于AI任务”定向增强”，比如根据识别任务去噪、增强边缘对比度，让机器更容易提取特征，把不相关的背景信息直接过滤掉；
  • Bit truncation（比特截断）：降低位深。机器识别主要靠亮度轮廓，直接把代表精度的比特位截掉即可。

中间部分（解码器VTM）：直接将编码端处理后的数据喂给VTM引擎去压缩。

右侧部分（解码端）：

  • Bit enhancement（比特增强）：补齐被截断的比特位；
  • Temporal restoration（时域恢复）：把降低的帧率恢复到原来的平滑度；
  • Spatial restoration（空域恢复）：把降低的分辨率用超分算法恢复上去；
  • Task-based restoration（基于任务的恢复）：根据AI任务的需求，重建出被去掉的特征。

FCM技术路线

FCM是作为一个过渡到VCM的技术路线，核心思路是直接压缩特征。

  • 核心流程：提取中间特征（Intermediate features） -> 特征降维（降采样/多尺度特征重建，把没用的特征丢弃） -> 特征转换（打包、量化，变成二进制） -> 特征内核编码（Feature Inner Coding）。

中间部分的内容表示出，FCM为内核编码提供传统的成熟H.264、H.266/VVC编码器外，还提供超先验神经熵编码器（deepCABAC），同时包含了PCA、时域重采样、感兴趣区域选择等经典算法。

DCM技术方案

DCM展现的是未来最终的编码方案，完全抛弃传统视频编码规则，端到端使用深度神经网络来压缩图像。

编码端（左侧）：

  • 输入图像 → 特征提取模块：图像首先进入特征提取网络（由Conv3x3、LeakyReLU、Conv1x1、GDN等构成），这个网络负责把像素级的图像转换成一个压缩的特征张量Y；
  • 正交变换模块 & 量化模块（Q）：通过量化（Q）操作，把神经网络算出来的连续小数变成离散的整数；
  • 可变码率模块：通过超先验网络控制量化的步长。

超先验与上下文模型：

  • 超先验获取模块：从主特征Y中提取出另一个更小的特征Z（超先验）；
  • 上下文估计模块、均值估计模块、方差估计模块：这组成了上下文模型。它利用前面已经解码出来的数据（利用自回归或注意力机制），结合Z，实时预测当前数据块的概率。预测得越准，熵编码（AE/AD）压缩得越多。右侧的红蓝相间的模块（Conv1x1、GDN、LeakyReLU）是用来计算这些概率参数的神经网络。

解码端（右侧底部）：

  • 特征匹配模块 & 重建模块：解码头接收到量化后的特征Yhat后，通过反量化、逆向变换，最后经过一系列神经网络进行重建。

五、《解耦·共享·增效：CXL内存池化的场景验证》

主要问题：AI模型参数暴增，服务器对HBM和DDR的需求激增。但HBM受限于GPU封装难以扩展；传统DDR受限于DIMM插槽数量，扩展往往需要连带升级昂贵的CPU和主板；SSD虽然便宜，但IO路径长、延迟高，不适合高性能场景。

为了解决上述的问题，提出了CMM-D高性能内存拓展器。采用CXL 2.0 & PCIe 5.0标准，单卡最高256GB，带宽可达36GB/s，延迟约110ns。

它的关键是能脱离CPU主板独立插拔。

基于CMM-D的硬件支撑，提出了CXL池化方案：

  • 基于RDMA的内存池化：通过网线扩展内存，依赖外部服务器，TCO极高，且性能受网络限制；
  • 基于CXL的内存池化：通过CXL交换机扩展，不依赖服务器，无需网卡，TCO极低，且提供硬件级的内存一致性。

为了验证基于CXL的内存池化的表现，实测了在三种典型高负载场景下的表现：

场景一：Redis集群

传统的Redis扩容必须”Scale-out”（买新CPU和主板），且冷热数据不均会导致负载不均衡，数据迁移会造成性能损失。

基于CXL内存池化的Redis集群方案的核心是：引入CXL Switch，将Redis内存池化。将Value放在CXL Switch后面的共享内存池中，而Key保留在本地节点的DRAM中。

通过CXL内存共享，热点节点的内存压力可以由CXL共享池中的空闲空间去分担，实现了零拷贝的负载均衡。

在Intel Xeon CPU、256GB DDR5、两块256GB的CMM-D、Redis 7.2.4，并使用业界标准的YCSB “All read”负载测试下，对比传统的RDMA Redis，CXL Redis的吞吐性能提升了41%，负载均衡时间缩短了46%。

场景二：LLM KV Cache

随着上下文变长，KV Cache爆炸式增长，GPU显存和主机内存不够；用SSD卸载延迟太高；用RDMA卸载成本太高。

方案核心是：将CMM-D接入vLLM推理系统，通过修改内核将其视为独立NUMA节点，并修改LMCache支持CXL内存Pinning，让GPU能高效直访CXL内存。

软件上：

  • 修改内核：将CMM-D识别为独立NUMA节点；
  • 修改LMCache：使其支持以交织的方式访问CXL switch的内存池，让大模型不把数据只留在本地；
  • 配置内存固定：GPU绕过CPU，直接通过PCIe/CXL通道访问远端的CXL内存池。

硬件上：

  • 计算端：有两个CPU（CPU0/CPU1），连接着各自的本地DIMM以及本地的E3.S 2T插槽；
  • 网络/交换层：CPU通过PCIe交换机连接到CXL Switch；
  • 异构算力端（GPU/DSP）：在CXL Switch下方，连接着DSP，下面挂着GPU和M200等加速卡。

在常规容量下，经过适配修改后的CXL方案吞吐性能已与原生DRAM基本持平；而当KV Cache容量超过DRAM极限触发重算时，CXL switch方案可提供5.6倍的有效容量扩展，并依然维持约36万TPS的高吞吐性能。

场景三：MySQL NDB分布式数据库

数据节点与SQL节点之间，依赖传统的TCP/IP或RDMA网络通信，小数据包高频传输时，网络延迟成为了巨大瓶颈。

方案核心是：用CXL Switch直接取代网络交换机，把原本需要通过网线传输的数据变成了内存级直接访问。

数据节点检索到数据后，直接写入CXL内存；SQL节点直接从CXL内存里读数据，绕过了网络协议栈和网卡，实现了零拷贝共享。同时，CXL内存池还可以扩展数据的缓冲池，加速数据获取。

在Intel Xeon CPU、1TB DDR5、两块256GB的CMM-D、MySQL NDB分布式数据库下，对比传统的RDMA MySQL，CXL MySQL的系统总吞吐量提升了17%，其中写入场景性能提升幅度最大，达到了17.4%。

六、《KVoF：KV时代的Fabric协议》

背景

  • 趋势一：KVCache，以存代算。 大模型无论是全注意力还是线性注意力，KV重算的代价都极其高昂。只要存下KV，就能免去重算（以存代算）。行业印证：Mooncake以KVCache为核心做PD分离与分层缓存，吞吐提升75%。
  • 趋势二：序列M级增长——分级缓存。 主流模型上下文已从4k涨到1M甚至4M以上，1M上下文约需70GB的KV。容量巨大，单点XPU（GPU）显存放不下，必须层层下移（HBM → DRAM → SCM → SSD），但每下一层时延增加10-100倍，成本大降。层与层之间需要高性能、差异化的连接与访问。
  • 趋势三：Agent记忆——KV持久化+向量记忆。 Agent任务跨会话、跨轮次，需要长期记忆和短期记忆。这种”可写、共享、跨会话”的记忆，要求按Key内容寻址、细粒度随机读，且对时延极敏感。两类记忆（KV和向量）统一在同一个数据面承载。

挑战

这里主要总结了当前面临的一些挑战：

  1. 多后端协议兼容，适配爆炸：DRAM、3FS、SSD、对象存储协议各异，推理框架需要做N×M适配，重复造轮子；
  2. 异构介质访问，语义断层：介质有快有慢，网络有机内、机间、集群。冷热/优先级/TTL语义无法统一，无法做到在对的时间，把对的KV放到对的层；
  3. 性能（512B小IO @ 100M IOPS）：NVMe时代的命题是4KB@1M IOPS，而KV时代变成了512B@100M IOPS。这是”IOPS bound”而不是带宽问题，必须通过深度流水线、预取和协议层聚合来压榨出性能；
  4. XPU自身开销，算力被浪费：最贵的是XPU，但它被当作”二传手”，要处理拷贝、内存bounce buffer、网络协议栈、网卡doorbell，挤占了宝贵的Decode算力。目标是XPU Near-Zero Overhead（近零开销）。

为了解决上面提到的一些问题/挑战，提出了KVoF协议（面向KV数据对象的开放传输协议，连接推理应用与多级存储介质）：

主要目的是：统一KV数据在大模型推理环境下的访问和传输标准。

  • 数据传输层：摒弃CPU作为中间缓冲，利用RDMA和CXL的硬件地址翻译原语。XPU直接登记自己的显存物理地址，网卡或CXL交换机收到请求后，直接将数据包通过PCIe总线写入显存地址。CPU完全不感知数据搬运，无内核态切换，无内存拷贝。对于CXL，主机内存池化后，KV数据直接映射进XPU的地址空间，XPU直接通过Load/Store指令读取远端内存；
  • 事务层：IO聚合与分散聚集结合：KVoF在传输层里实现了批量聚合提交，软件层把同一批次内成百上千个稀疏的512B请求合并成一个大的传输事务，利用大包的高带宽传输；接收端通过Scatter-Gather List将网络包拆解，精准投递到XPU显存中对应的分散地址，减少单次IO开销，充分利用硬件传输效率；
  • 寻址与路由：控制面与数据面分离的硬件加速引擎：控制面（CPU）运行在普通CPU上，负责计算KV的冷热度、Namespace管理、QoS策略，并将”逻辑Key到物理地址”的映射表通过低速控制通道下发到DPU/NIC的内存中；数据面（DPU/NIC）里面固化了一个专门的KV解析与查找引擎，当收到KV请求时，硬件直接在本地SRAM中查表，找到物理地址，直接发起DMA读，查询过程完全不产生CPU中断，不触发系统调用；
  • XPU调度：异步流水线与计算通信重叠：协议栈在XPU侧提供了一套异步提交原语。XPU发起IO请求后，马上返回去算下一层（Layer i+1）的注意力。当数据通过RDMA到达显存后，网卡向XPU发出一个轻量中断或Doorbell，XPU直接去取数据。

统一寻址格式：不同推理框架底层寻址方式完全不同，这就导致了同一份KV，换个框架就无法寻址，底层存储系统无法统一管理。为了解决这个问题，定义了一个统一的寻址格式，包含{模型/版本/层, token块/前缀hash, dtype, 生命周期元数据}。这时同内容同Key，因为是按内容哈希寻址，所以天然支持前缀复用与跨实例去重。

XPU直通IO：传统路径为存储 -> 网络 -> CPU -> XPU，数据要先拷到CPU内存，CPU再处理网络协议栈，最后再拷给GPU，极大地浪费了昂贵的CPU算力，并增加极高延迟。为了解决这个问题，KVoF让XPU直接发起并完成KV IO，路径变为存储 -> 网络 -> XPU：

XPU直接向存储发起读写请求，数据通过RDMA/CXL直达XPU显存。

此外，KVoF直接把KV语义硬化进DPU / 网卡 / 存储控制器，让硬件直接处理KV指令：

  1. Key解析与路由：硬件直接理解KV寻址，不再需要CPU解析复杂的哈希；
  2. 放置查找：元数据查询不出芯片，大幅降低访问延迟；
  3. IO聚合：针对模型产生的海量小IO，在硬件内部进行聚合，碎片不下发，提升网络利用率；
  4. 协议栈offload：传输协议全流程卸载到硬件，彻底绕开CPU处理网络协议栈的开销。

为了进一步消除GPU（XPU）空转，解决海量小IO和稀疏读取带来的性能损耗，KVoF通过以下方法实现：

  1. 批量聚合提交：将模型产生的多个离散且微小的KV块，合并为一次大的IO请求，按批聚合；
  2. 异步流水线：IO提交与Attention计算重叠，XPU发起IO后不等数据，而是继续算当前层；
  3. 稀疏访问下沉：稀疏查找、元数据访问等任务，下放到底层硬件（DPU/网卡）。

八、《智算存储技术发展与生态构建》

大模型训练过程全生命周期为：数据采集、数据预处理、模型训练、推理。

整个过程中，IO特征矩阵为：

  • 预处理：多线程、小IO（KB级）、顺序读、系统吞吐性能强；
  • 训练CheckPoint写/断点续训读：多线程、大IO（MB级）、顺序读写、多文件（GB级）；
  • 推理模型加载：多线程、大IO（MB级）、顺序读；
  • 推理KV Cache读写：多线程、混合IO（KB+MB级）、随机读写、系统吞吐性能强；
  • 推理Prefill/Decode：多线程、小IO（KB级）、混合随机读写。

数据预处理时，数据会加载到服务器内存中，由CPU进行解码、格式转换、数据增强，再批量送给GPU。此时，系统需要具备极高的系统吞吐性能，且要能扛住海量小文件元数据操作的巨大压力。

训练过程CheckPoint：在训练过程中大约每2小时保存一次，需要所有GPU卡并发写出大IO的多个大文件。这种”周期性、瞬时性”的巨大带宽需求，不仅给存储网络带来巨大的冲刷压力，还造成了昂贵的GPU算力白白停滞。

模型推理阶段的特征相反：在模型加载时，多线程大IO顺序读多个大文件，主要靠系统吞吐性能；KVCache缓存读写是多线程、混合IO，不仅顺序读多个大文件，还有随机的读写请求，且要求系统高吞吐；推理Prefill/Decode时，则是多线程、小IO、混合随机读写多个大文件。传统SSD和文件系统擅长顺序大块读取，而稀疏注意力机制产生的是大量的512B小IO随机读取，导致存储系统无法有效利用带宽，引发严重的CPU Bubble。

常见的解决方案

软件/文件系统侧：

1）DeepSeek（3FS分布式文件系统）方案：

  • 架构：HBM池化 + 外置存储，通过”Prefill Load Balancer”和”Decode Load Balancer”将任务分发；
  • 核心技术：将Token上下文的Key-Value数据，通过3FS分布式文件系统，以”小文件合并成大文件”的方式，基于POSIX接口，直接卸载至外部KV Cache Storage；
  • 特点：极度依赖并行文件系统（3FS）的超大带宽来满足7.2 Tbps的高速CXL接口，通过多级池化有效降低了内存成本。

2）Mooncake（PD分离+存算分离）方案：

  • 架构：将Prefill（预填充）和Decode（解码）节点彻底分离，将GPU集群的DRAM、SSD等存储资源组合成一个分布式的多级KVCache缓存资源池（GPU显存 -> 主机内存 -> 本地SSD）；
  • 优化目标：对Prefill阶段优化”Max Cache Reuse”和”TTFT SLO（首字延迟）”；对Decode阶段优化”Max Throughput”；
  • 特点：通过精细的KVCache管理，实现”以存代算”。

硬件侧：

1）NVIDIA ICMS（Inference Context Memory Storage）+ 华为：

  • 加速手段：通过BlueField-4 DPU硬件加速，实现跨节点的KV Cache共享和低时延访问；
  • 华为”超节点”存储分层定义（G1-G4）：
    • G1 GPU HBM（100GB，纳秒级）
    • G2 系统DRAM（TB级，10-100纳秒）
    • G3 本地SSD（10-100微秒）
    • G3.5 Context Memory Storage（PB级，超节点共享，针对复用KV）
    • G4 温存储（毫秒级）

2）中兴：

  • 核心设计：引入”计算侧DH DPU（ZMS多级推理上下文管理平台）”，GPU与底层SSD之间通过KV服务接口直接通信，通过交换网络连接；
  • 控制流与数据流分离：图中红线为控制流，蓝线为数据流。控制流通过DPU下发，数据流通过NVMe over KV、Fabric直通，支持GPU直通存储、设备侧NVMe over KV和双端口盘访问；
  • 特点：本质上是将KV Cache的存储引擎完全”下沉”到DPU芯片中，绕过CPU，实现了近零开销和极高IOPS。

KVCache生态的接口不统一问题

这里表达了上层软件生态上KVCache存储管理与适配的接口不统一：当前各家KVCache方案各不相同，推理引擎（MindIE、vLLM、SGLang）接口互不兼容，导致底层存储无法实现高效统一管理。

主要从4个维度介绍：

  1. 多级架构（硬件层）：分L1（HBM显存）、L2（DRAM内存）、L3（本机/外置SSD）。业界目前有两大派系：以Mooncake为主的HBM+DRAM+SSD，和以DeepSeek为主的HBM+外存，但没有成熟的多级组合指引；
  2. 缓存管理（中间层）：需要实现生命周期管理、热点数据管理、老化删除以及节点间KV调度协同；
  3. 接口适配（软件层）：各框架数据结构、API不同；存储厂家适配能力弱。面临两难选择：要么”每个存储适配多框架”（高效但复杂），要么”统一框架KV交互接口”（标准但效率未知）；
  4. 传输加速（网络层）：通过高性能存储、并行文件系统、RoCE网络、GPUDirect保障KV读取性能。

（需多方推动适配vLLM/SGLang/MindIE框架，推动KV交换接口成熟，共建KVCache多级缓存生态）

GPU直接访问存储技术（GDS）

核心概念：GDS（GPU Direct Storage）技术通过让GPU绕过CPU和系统内存，直接访问本地或远程存储设备（如NVMe SSD、网络存储），实现降低延迟、提高带宽、释放CPU资源。

传统IO路径（左图）：GPU显存 -> PCIe Switch -> NVMe/NIC -> 主机内存（CPU处理） -> SSD。存储系统需调用CPU内核接口，配置DMA地址，流程冗长。

直通技术核心（右图）：

  1. 路径简化与去中介化：移除CPU在数据传输中的调度、中断处理与拷贝职责；
  2. 建立直通管道：在GPU与存储设备之间建立端到端直达路径；
  3. 零拷贝（Zero-Copy）架构：数据从存储设备直达GPU显存，消除主机内存中的冗余缓冲；
  4. 高速互连释放：最大化利用PCIe/NVLink（本地）、RDMA over InfiniBand/RoCE（远程）或CXL（可扩展内存池）等超高速互连潜力。

（由于各GPU厂商接口不统一，需存储与GPU平台做一对一适配，当前正拉动行业构建国产GDS生态）

存储适配RAG系统的语义化接口

这里介绍了如何让底层存储直接适配大模型的知识库（RAG系统），通过语义化接口减少模型幻觉。

左图：RAG的完整生命周期（离线与在线）：

  • 离线阶段：外部文档注入 -> 文档解析 -> 文档切分（切片） -> 通过Embedding模型提取语义 -> 存入”向量数据库” -> 最终落盘到”存储系统”；
  • 在线阶段：用户提问 -> 推理智能问答（将问题向量化，通过RAG API去向量数据库检索） -> 提取相关片段 -> Rerank（重排序模型） -> 喂给LLM（大模型）生成最终回答。

RAG系统无论是”离线写入”还是”在线检索”，底层都需要高效率的存储系统来支撑。

右表：语义接口层（提供模型原生接口）——传统存储只懂”块”和”文件”，而AI懂的是”向量”、”张量”和”图谱”。因此存储必须提供三种AI原生接口：

  • 接口1：向量原生
    • 核心功能：支持近似最近邻（ANN）搜索（找最相似的向量）；支持基于向量ID或内容的相似性检索；支持批量向量写入与流式写入；
    • 应用场景：RAG系统、推荐系统、相似性去重，这是当前最主流的接口；
  • 接口2：张量原生
    • 核心功能：支持多维张量（比如多维度矩阵）的高效切片、转置、分块读取；支持张量的并行I/O接口，适配模型并行训练；优化小尺寸张量的高并发读取；
    • 应用场景：模型训练与推理、特征库管理，这能极大地减少CPU去拆解复杂数组的负担；
  • 接口3：RAG图谱原生
    • 核心功能：协同存储向量、原文块及它们之间的复杂关系（也就是图结构）；支持在图谱上进行多跳查询与子图检索；
    • 应用场景：复杂知识推理、事理图谱分析。传统存储存图很难，原生图谱接口能直接跑通逻辑链路。

总结

这场存储系统论坛的议题高度聚焦在AI推理时代的存储新命题上，可以提炼出几条贯穿全场的主线：

  1. KVCache成为AI存储的核心战场：几乎所有议题（阿里云Fusion Cache、Xcache、KVoF、KVCache测试、智算生态）都在回答同一个问题——如何把KVCache放得下、取得快、管得好。”以存代算”已成共识，缓存命中与重算的”黄金交叉点”是决策核心；
  2. CPU成为新瓶颈，硬件直通是共同答案：从DPU卸载、GDS、KVoF的XPU直通到中兴的KV下沉DPU，各家方案殊途同归——让数据绕过CPU直达GPU/XPU；
  3. 分层与解耦是TCO的最优解：从西部数据的SMR/CMR/QLC介质分层（1EB容量5年差6倍成本），到G1-G4多级KVCache缓存，”在对的时间把对的数据放在对的层”是贯穿硬件和软件的设计哲学；
  4. CXL从概念走向场景验证：Redis（吞吐+41%）、LLM KVCache（5.6倍容量扩展）、MySQL NDB（吞吐+17%）三个实测场景给出了量化答案；
  5. 生态碎片化是当前最大痛点：推理引擎接口不统一、GPU厂商GDS接口各异、KV寻址格式不同，标准化（KVoF协议、统一寻址）是行业下一步的努力方向。

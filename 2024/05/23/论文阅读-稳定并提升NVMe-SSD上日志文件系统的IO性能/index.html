论文：Stabilizing and Boosting I/O Performance for File Systems with Journaling on NVMe SSD

问题：SSD做外部日志设备时的性能波动

许多日志文件系统（在写入数据时，先将相关信息写入日志，再将数据写入底层存储设备）使用SSD来作为外部日志设备以提高I/O性能。但是在微小写入工作负载时，会产生严重的I/O波动，==主要原因是因为将数据写回到硬盘驱动器（HDD）上的后端文件系统比写入日志的速度慢得多。==

由于两阶段机制（two-phase mechanism）的存在，这导致日志写入频繁冻结：微小写入通常涉及许多小规模的数据写入操作，这些操作通常是随机且高频的，这意味着系统必须频繁地处理多个独立的写入请求，每次请求可能只写入少量数据。虽然日志的写入速度非常快，但是写回速度很慢，这时写回队列（Writeback Queue）会经常被填满。==写回队列一旦满了，系统就无法继续进行新的日志写入操作，这会导致日志写入的能力冻结/暂停。=

综上可以得到：

  1. SSD的IOPS性能波动较大，且大部分时间SSD处于冻结状态；
  2. IOPS性能的稳定性与微写大小密切相关，而与线程数关系不大（因为锁机制的存在），==微写大小越小，IOPS性能波动越严重==（因为对于较大的写入操作，可以有效地利用HDD的顺序写能力）。

解决方案：内存合并加速架构（MIM）

主要思想：==造成上述问题的主要原因是回写速度慢。由于HDD的顺序写速度比随机微写入速度快，因此将多个微小写入操作合并成顺序的大块写入（sequential large writes）并暂时保存在内存中，然后再将这些大块数据写回到后端存储设备中。=

这个设计需要解决三个问题：

1. 快速识别相同地址的微小写入：要合并多个微小写入，它们必须具有相同的地址（即相同的目录和对象）。识别这些相同地址的操作需要非常快，否则这个识别过程本身可能成为性能提升的新瓶颈。==论文引入了一种新型的基于开放地址散列表的多链表（HTMLL，Open-Address Hash Table-Based Multiple Linked-List）数据结构，这种数据结构不仅能有效地支持写入操作的合并，还能在将数据刷新（flush）到底层存储设备时带来额外的好处，如减少冲刷时间和提高效率。=

2. 增加合并机会的内存滞留：为了增加合并的机会，每个微小写入在内存中保留的时间需要相对较长。然而这会推迟微小写入的写回时间，从而增加日志队列被填满的可能性，导致新的写入操作需要等待。==论文采用了一种新的刷新机制，这一机制考虑了HTMLL的占用率（occupancy ratio）以及时间因素，在不影响性能的前提下优化合并操作的时机和刷新操作，从而避免日志队列的拥塞。=

3. 写入操作重排序引发的问题：由于合并操作会导致写入操作的重排序，原本的检查点机制（checkpointing mechanism）可能会失去其功能性，导致系统在崩溃时无法正确恢复数据。==论文对原有的检查点机制进行了重新设计，以应对由于合并操作导致的写入操作重排序问题，确保系统在发生崩溃时仍能正确恢复数据。=

与传统的日志文件系统的区别是：(1)将传统的Flush操作分成了2个过程；(2)新增了Check pointing（检查点）操作。

Flush Phase 1：HTMLL——解决怎么快速识别相同地址的微小写入

将每个微写入操作都用一个四元组来表示：<cid,oid,sn,data>，其中：

  • cid：对象组的标识符，可以理解为微小写入操作要执行的目录，不同的对象组有不同的cid；
  • oid：对象组内某个对象的标识符，即数据要写入的具体对象（不同的cid之间可以共享一组oid值）；
  • sn：微小写入操作的序列号；
  • data：要写入文件系统的数据本身。

==将对象组的数量设置较多、对象的数量设置较少时，可以减少定位对象的时间。=

上图为HTMLL的数据结构图。具体来说：==在线程池中的每一个线程，首先都会被映射为形如<cid,oid,sn,data>的四元组的格式；然后哈希表被分为多个（N个）槽，每个槽都是一个链表的起始点，每条链表都是由多个（M个）链块构成，链块上有多个进程。之所以把这些进程放在一起组成一个链块，是为了方便将这些随机写的进程合并为一个大的顺序写的进程（可以选择适当的M和N的值来控制内存消耗）。=

线程进入HTMLL的具体过程：当有新的微写入操作到达HTMLL时，首先会根据其oid来决定它应该被放到哪个槽中（同一个槽/链表上的链块具有相同的oid）。如果成功，写线程接下来会检查该槽对应的链表，看看链表中是否存在一个与cid匹配的链块。如果在这个链表中没有找到与cid匹配的链块，说明这个链表中没有与这个微写入操作相关的已有数据，此时系统会将这个微写入操作直接写入到写回队列中。如果找到了匹配的链块，系统会将新的数据追加到这个链块中——这意味着多个属于同一对象组的微写入操作会被合并在同一个链块中，以便在后续的写回操作中一次性写入。如果失败（即哈希表中所有的槽都被占用，没有空槽且其oid和现有的oid都不匹配），则会将这个操作直接写入写回队列，不进行后续的合并处理。

Flush Phase 2：空间阈值与时间阈值——解决内存滞留问题

在MIM架构中，微写入操作通常会在HTMLL中停留一段时间，以便有更多机会与其他微写入操作合并。但是如果HTMLL中的占用率过高（有太多的链块已经被占用），那么新的微写入操作将直接被刷新到写回队列中，而无法充分利用合并的优势。这不仅减少了合并带来的性能提升，还可能导致检查点日志（checkpoint-based journal）变得过大，进而严重影响系统性能。因此提出了空间阈值和时间阈值：

空间阈值（基于HTMLL的占用率，即占用的链块比例）：

其中：

  • journalthroughput：NVMe SSD在追加微写入操作时的固有最大吞吐量，即它能以多快的速度处理这些写入操作；
  • max flushing intvl：两次连续的日志刷写操作之间的最大时间间隔，这个间隔由文件系统指定，在这个时间间隔内，日志系统会定期将数据从HTMLL中刷写到写回队列中；
  • blocksize：一个对象（object）的大小，即每个链块的大小；
  • sp_thresh：在最大刷写间隔内，系统需要分配的链块数量。

==journalthroughput × max flushing intvl 得到的是在max flushing intvl这么长的时间内有多少数据写入进来，然后计算得到的总数据量除以blocksize（对象或链块的大小）后，得到的数字表示在最大刷写时间内需要多少个链块才能容纳这些数据量。=

==考虑到写入操作时，可能需要等待数据的所有副本都成功写入、或者所有节点都同步完毕之后，才能继续进行下一步操作。这种等待时间会影响整体的写入效率，因此用其来定义时间阈值。=

==当HTMLL的占用率超过了空间阈值、或者距离上一次刷写操作的时间超过了时间阈值时，写线程将停止将新的微写入操作插入到HTMLL中，随后系统将触发一个整体的刷写操作。=

Record-Checkpoint：解决写入操作重排序后的数据一致性问题

在传统的日志文件系统中，微写操作按照附加到日志文件的顺序写回操作系统。日志文件中存在一个检查点，这个检查点会定期更新，表示最后一次检查时未写回操作系统的第一个微写操作。由于是按顺序写回，所以这个检查点之后的所有微写操作都被视为未写回。==但是在MIM体系结构中，由于合并操作的存在，在日志中落后于一个微写操作的另一个微写操作可能会被提前写回，因此只记录最后一个完成写回操作的检查点机制是会产生问题的。=

解决办法：首先记录自上一个检查点后，所有成功写回到底层文件系统的微写入操作的序列号（sn）。这些成功的sn会被保存到一个辅助链表中，并按照它们在日志文件中的顺序排列。系统随后会通过辅助链表来找到检查点可以更新的位置。具体来说，==系统会从当前检查点开始，逐一检查这些成功写回的sn：如果检查点的sn与辅助链表中最早的sn相同，说明这个微写操作已经成功写回，检查点就可以向前移动到下一个未被成功写回的微写操作的位置。==通过重复这一过程，系统不断更新检查点，直到遇到一个sn在链表中没有匹配的情况。

总结

在使用SSD作为外部日志的日志文件系统中，SSD的写入速度远大于HDD的写入速度，因此会导致性能波动等问题。论文提出了一种名为MIM（Merging-In-Memory）的优化架构，通过微写合并操作来提升效率，同时解决了这个框架带来的三个问题：

  1. 如何高效合并微写操作——HTMLL数据结构；
  2. 如何在最合适的时机触发写回操作——空间阈值+时间阈值；
  3. 如何确保合并操作后的数据持久性和一致性——Record-Checkpoint机制。

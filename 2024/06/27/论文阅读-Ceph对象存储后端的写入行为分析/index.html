论文阅读：理解Ceph对象存储中存储后端的写入行为

论文：Understanding Write Behaviors of Storage Backends in Ceph Object Store

概述

论文作者对Ceph提供的三种存储后端（FileStore、KStore和BlueStore）通过微基准测试与长期工作负载的综合分析进行了测试，主要聚焦于WAF（写放大系数）。

核心发现：==不管是哪种存储后端，WAF都大于13==。其中BlueStore的综合性能最稳定，FileStore在SSD上的表现最好，BlueStore在HDD上表现不错。

这三种存储后端的写放大的来源如下：

FileStore：需要先将数据写入独立的journal（日志设备），然后再写入主存储区。这本应是”双写（double write）”，即写流量为2倍，但实验发现实际是3倍。因为文件系统本身也有自己的日志系统，即数据流程变成：数据 → Ceph journal → 文件系统 → 文件系统 journal → 真正写入位置。==结果导致：文件系统的元数据+日志流量 ≈ 原始数据量大小，写放大更严重。==

KStore：KStore采用RocksDB存储元数据。由于RocksDB的LSM-tree结构，后台会进行大量compaction。实验发现：==几乎所有写流量都来自compaction，而不是用户写入的数据。==

BlueStore：数据直接写入裸设备，不经过文件系统，因此它避免了FileStore的journaling of journal问题。但是它的写放大依旧存在，主要来源是”Ceph仍使用RocksDB存储元数据和对象属性”，这些RocksDB写流量的大小超过真实数据写入量的3倍。简而言之：BlueStore解决了日志嵌套的问题，但RocksDB的元数据写放大仍然很严重。

Background

Ceph的三种存储接口

存储类型 描述 举例
对象存储（Object Storage） 类似 Amazon S3、Swift，存储对象（Object） Ceph Object Storage（RADOS Gateway）
块存储（Block Storage） 给虚拟机或系统提供块设备 Ceph RBD（RADOS Block Device）
文件系统（File System） 类似分布式文件系统 CephFS

虽然提供三种不同形态的服务，但它们的底层都是建立在同一个统一核心：==RADOS==（Reliable Autonomic Distributed Object Store）之上。RADOS层运行着Ceph内部的关键组件：

名称 全称 是否是守护进程（Daemon） 是否运行在 RADOS 层？ 作用
MON Monitor ✅ 是 ✅ 是 保存并管理集群状态（如 OSD 列表、集群地图），负责一致性和选举
MDS Metadata Server ✅ 是 ✅ 是（但只用于 CephFS 文件系统） 管理文件系统的目录、权限和名称等元数据
OSD Object Storage Daemon ✅ 是 ✅ 是 存储数据对象、处理读写请求、执行数据复制和恢复

Ceph与传统分布式存储的区别

  1. 客户端可以直接联系负责该数据的主OSD节点（primary OSD），无需中间服务器；
  2. 不需要固定的元数据服务器来告诉客户端”数据在哪里”；
  3. 数据的位置是通过CRUSH算法算出来的，而不是查表得到。

BlueStore的定位

BlueStore是Ceph的另一种存储后端，其核心理念在于高效管理对象数据，突破FileStore的局限性。FileStore存在的问题之一是外部日志记录导致的双重写入开销。BlueStore则直接将对象数据存储于原始块设备，同时使用RocksDB管理元数据。由于跳过了本地文件系统层，可规避日志记录等文件系统开销。

需注意的是，由于运行RocksDB仍需文件系统支持，BlueStore内部集成了名为BlueFS的轻量级用户级文件系统。此外，Ceph通常需处理大量对象，且常需按顺序枚举所有对象以进行一致性检查和恢复，然而POSIX并未提供从多个目录高效检索对象的方法。使用RocksDB的另一优势在于，Ceph能够轻松检索并枚举系统中存储的所有对象。

微基准测试结果

FileStore

4KB写入在Ceph内部的路径为：

(1) 客户端定位数据应该写到哪个OSD

客户端通过CRUSH算法在O(1)时间内计算出负责该对象的主OSD，然后将写请求发送给主OSD。

(2) 写副本

主OSD将写请求转发给另外两个OSD（即副本#2和副本#3）。因为副本机制（replication factor = 3），这一步本身就会产生3倍流量。

(3) 在每个OSD内部，数据会被打包成一个”事务”

内容 作用
对象数据（object data） 你写入的 4KB 数据
对象元数据（object metadata） 比如对象大小、时间戳、offset 等
LevelDB（或 RocksDB）键值对 存储对象索引与属性，用来快速定位和管理对象

(4) FileStore接收到这个事务后，会做两件事（双写来源）：

  1. 先写Ceph Journal（预写日志，Write-Ahead Logging）：保护事务的原子性（可崩溃恢复），这是第一部分写放大来源；

  2. 再把这份事务写入XFS（真实数据 + LevelDB数据 + 文件系统元数据）：

    • 真实文件写入 = object data；
    • LevelDB的写放大（LSM-tree会产生compaction）；
    • XFS文件系统写元数据 + XFS Journaling。

    这是第二次写放大，导致”journal of journal（日志的日志）”问题。

所以4KB写入的WAF因子很大且有波动性，但是随着写入请求大小的增大，直至4MB时，WAF收敛至6，因为相对于请求大小，对象元数据、键值对、文件系统元数据和文件系统日志的占比会相对缩小。

BlueStore

可以发现第3次写（3rd Write）的WAF很高，论文解释原因为：BlueStore按最小分配粒度 = 64KB Chunk来管理数据。当写入请求落在某个Chunk中间、且打破了它的连续性时，BlueStore必须做：==把当前64KB Chunk中未写满的部分用零填充（zero padding），然后整个64KB写入磁盘。==

笔者注：在Ceph官网实际调研后发现，现在BlueStore默认的最小分配粒度已经是4KB了，也就是说这里补0带来的WAF应该已经没有了。总体上BlueStore效果更好，因为没有了日志双写问题。

总结

这篇论文的价值在于系统性地量化了Ceph三种存储后端的写放大来源：

后端 主要写放大来源 关键问题
FileStore Journal双写 + 文件系统日志（journal of journal） 双写实际为3倍而非2倍
KStore RocksDB的LSM-tree compaction 写流量几乎全来自compaction
BlueStore RocksDB元数据写流量（超过真实数据3倍） 解决了日志嵌套但元数据放大仍在

结论指向一个明确的方向：分布式存储系统的后端如果想进一步降低写放大，要么换掉LSM-tree的元数据方案，要么优化元数据的落盘路径——这也与后续一系列针对RocksDB/BlueStore的优化工作（如MatrixKV、就地更新方案等）相呼应。
